Review a **pull request** on two independent axes and **post the report on the PR** — the review that only ever existed in a terminated session did not happen. This skill reviews; it does not fix (failing checks and requested changes route back to `/tdd`), and it assumes it is running in a **fresh context** that never saw the code written — that independence is the point of the stage.

Adapted from aihero.dev's `/code-review` (see `research/aihero-spine.md` in blooop/wayfinder): two-axis report, parallel subagents, fail-fast preflight, and the Fowler baseline kept verbatim; the interactive inputs are made deterministic and the in-session report is rerouted to the PR.

## Invocation

`/review <pr>` — a PR number or URL (or a ticket number whose linked open PR is unambiguous). Resolve the repo explicitly and pass `--repo` on every `gh` call.

## Inputs — deterministic, never asked

- **Fixed point**: the PR's merge-base with its base branch. Capture the diff command once: `git diff <merge-base>...HEAD` (three-dot).
- **Spec**: the ticket the PR closes (`Closes #n` / the Development link). Fallback order: issue references in the branch's commit messages, then a spec file the ticket links. **If no spec is found, the Spec axis reports "no spec available"** — never infer the spec from the code.

**Fail-fast preflight, before spawning any subagent**: confirm the fixed point resolves (`git rev-parse`), the diff is non-empty, and the PR's checks are green. A bad ref, empty diff, or red checks fails here — comment on the ticket and stop; red checks mean the node is still `needs attention` and belongs to `/tdd`.

## The two axes — parallel subagents, never merged

Run both as **parallel subagents** so they don't pollute each other's context. Each axis reports at most ~400 words. Do **not** merge or rerank findings across axes — code that follows every standard but implements the wrong thing must fail Spec while passing Standards, and vice versa.

- **`## Standards`** — repo-documented standards first (**the repo overrides**), plus the fixed Fowler 12-smell baseline: Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest. Always a judgement call; skip anything tooling already enforces. This axis owns the refactoring conversation `/tdd` refused to have.
- **`## Spec`** — the diff against the ticket's stated behavior and acceptance criteria. Every Spec finding quotes a line of the spec. With no spec available, say so instead of listing requirements inferred from the code.

## Output — posted, so the gate is checkable

1. Post the two-axis report as a **PR review**, opening with the provenance line: `> *This was generated by AI during review.*` **State the verdict as the report's last section** — `Request changes` / `Comment` / `Approve` with the blocking findings enumerated — because the review *state* is not always available to you: GitHub refuses both `--request-changes` and `--approve` on a PR authored by the same account, which is the normal case when an agent reviews an agent's work. Fall back to `--comment` when that happens; the written verdict is what the gate reads, not the GitHub state.
2. Post a one-line gist breadcrumb on the ticket: verdict + PR link.
3. **Stop.** Do not fix findings (that is a `/tdd` launch on the now-`needs attention` node), and do not merge — merging stays human unless the run was explicitly steered otherwise.
